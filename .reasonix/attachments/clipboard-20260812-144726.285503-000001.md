You are a senior software engineer, security reviewer, and software architect. Perform a comprehensive code review of the entire application, not just individual files.

## Objective
Identify correctness issues, bugs, security vulnerabilities, performance problems, architectural weaknesses, maintainability concerns, reliability risks, and opportunities for improvement across the whole codebase.

## Review process
1. Inspect the repository structure and identify the application's:
   - Frontend and backend
   - Entry points
   - Core business logic
   - APIs and integrations
   - Database/data layer
   - Authentication and authorization
   - Configuration and environment handling
   - Tests
   - Build/deployment infrastructure
   - Dependencies

2. Trace important end-to-end flows rather than reviewing files in isolation.

3. Look for:
   - Functional bugs and incorrect edge-case handling
   - Race conditions and concurrency issues
   - Security vulnerabilities, including injection, authentication/authorization flaws, secrets exposure, insecure data handling, and dependency risks
   - Error handling and failure-recovery problems
   - Performance and scalability bottlenecks
   - Memory/resource leaks
   - Poor database queries or inefficient I/O
   - API contract and validation issues
   - State-management problems
   - Dead, duplicated, or unreachable code
   - Overly complex or fragile abstractions
   - Poor separation of concerns
   - Maintainability and readability issues
   - Missing or inadequate tests
   - Logging, monitoring, and observability gaps
   - Configuration and deployment risks
   - Backward-compatibility or migration concerns

4. Distinguish confirmed problems from potential risks. Do not report speculative issues as facts.

5. For every significant finding, provide:
   - Severity: Critical / High / Medium / Low
   - Exact file and line/function/component where possible
   - What is wrong
   - Why it matters
   - A concrete example or failure scenario
   - Recommended fix
   - Suggested implementation approach, including code when useful

6. Prioritize findings by real-world impact rather than by the number of issues discovered.

## Output format

### Executive Summary
Give an overall assessment of the application's quality and the most important risks.

### Critical Findings
List issues that could cause severe security, data-loss, availability, or correctness problems.

### High-Priority Findings
List the most important issues that should be addressed soon.

### Medium/Low-Priority Findings
Group less urgent improvements separately.

### Architecture & Design Review
Assess the application's architecture, boundaries, abstractions, dependencies, and scalability.

### Security Review
Provide a focused security assessment and identify concrete vulnerabilities or missing controls.

### Performance & Scalability Review
Identify likely bottlenecks and explain how they could affect the application as usage grows.

### Testing Review
Assess test coverage and quality, and identify important untested behavior.

### Technical-Debt Assessment
Identify areas where technical debt creates meaningful future risk.

### Recommended Action Plan
Create a prioritized remediation plan:
1. Immediate fixes
2. Short-term improvements
3. Longer-term architectural improvements

For each recommendation, explain its expected impact.

## Important constraints
- Review the whole application systematically before drawing conclusions.
- Do not merely summarize the code.
- Do not praise code unless it is relevant to a specific finding.
- Do not invent files, behavior, vulnerabilities, or line numbers.
- Avoid generic advice; tie recommendations to the actual codebase.
- Prefer evidence from the code over assumptions.
- When information is missing, explicitly state what could not be verified.
- If you identify a particularly risky code path, trace it through all relevant components and explain the end-to-end risk.
- At the end, provide the top 10 issues ranked by severity and impact.
